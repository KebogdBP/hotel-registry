# Project Vision и план реализации Hotel Registry

## Назначение проекта

Hotel Registry — конфигурация CRM для небольшой гостиницы. Она заменяет неструктурированные записи о телефонных обращениях единым процессом: администратор создаёт карточку бронирования, сохраняет данные гостя, перемещает обращение по понятным стадиям и видит историю прошлых визитов.

Это проект настройки Bitrix24, а не разработка отдельного сайта. Решение должно работать стандартными средствами бесплатного тарифа после отключения или окончания демо-режима. Такой подход сокращает срок реализации и исключает расходы на собственный сервер, подписку или дополнительное приложение.

Срок сдачи: **8 октября 2026 года, 19:00 по московскому времени**.

## Видение продукта

Администратор гостиницы открывает одну воронку и сразу понимает:

- какие обращения только поступили;
- по каким обращениям нужно уточнить детали;
- какие бронирования уже подтверждены;
- какие гости заселились;
- какие обращения завершились отказом.

При повторном звонке администратор находит гостя по телефону, использует существующий контакт и создаёт для него новую бронь. Предыдущие бронирования остаются связанными с тем же контактом и доступны из истории клиента.

## Проблема и ожидаемый эффект

### Исходная проблема

- Информация из звонков может храниться в блокноте, таблице или памяти администратора.
- Непонятно, кому уже ответили, а кому ещё нужно перезвонить.
- Отказы смешиваются с активными запросами.
- Повторного гостя могут зарегистрировать заново и потерять историю его визитов.

### Ожидаемый эффект

- Все обращения хранятся в одном месте.
- Текущее состояние бронирования видно на канбан-доске.
- Для отказов предусмотрен отдельный завершённый статус.
- Один гость имеет одну карточку контакта и несколько связанных бронирований.
- Рабочий процесс сохраняется после окончания пробного периода.

## Пользователи и роли

### Администратор гостиницы

Основной пользователь системы. Создаёт и обновляет контакты и бронирования, перемещает сделки по стадиям, фиксирует отказы и ищет историю гостя.

### Руководитель гостиницы

Просматривает текущие обращения и результаты работы. В рамках первой версии отдельная аналитика или специальные права доступа не настраиваются.

### Администратор портала

Один раз настраивает CRM: режим работы, поля карточки, стадии воронки и тестовые записи. Эта роль может совпадать с администратором гостиницы.

## Объём первой версии

### Входит в проект

- Один облачный портал Bitrix24.
- Бесплатный тариф без активного демо-режима.
- Простой режим CRM без лидов.
- Контакты для хранения гостей.
- Сделки для хранения обращений и бронирований.
- Одна воронка сделок.
- Пользовательские поля бронирования.
- Отдельная неуспешная стадия для отказа.
- История нескольких бронирований одного контакта.
- Тестовые данные для демонстрации.
- Короткое приёмочное видео.

### Не входит в первую версию

- Онлайн-бронирование для гостей.
- Публичный сайт гостиницы.
- Шахматка занятости номерного фонда.
- Автоматическая проверка доступности конкретного номера.
- Оплата, касса, счета и возвраты.
- Интеграция с телефонией, почтой или мессенджерами.
- Роботы, бизнес-процессы и автоматические уведомления.
- Несколько воронок или филиалов.
- Приложения из Маркетплейса.
- Миграция существующей клиентской базы.

Если клиенту позже понадобится фактическое распределение гостей по номерам или контроль пересечения дат, это станет отдельным этапом. Текущая версия управляет обращениями, а не номерным фондом.

## Основные архитектурные решения

| Бизнес-объект | Сущность Bitrix24 | Правило использования |
| --- | --- | --- |
| Гость | Контакт | Один человек должен иметь одну карточку контакта |
| Обращение или бронь | Сделка | Каждый новый запрос на даты проживания создаётся отдельной сделкой |
| История гостя | Связанные сделки контакта | Все прошлые и текущие бронирования связываются с одним контактом |
| Состояние обращения | Стадия сделки | Карточка перемещается по воронке вручную |
| Отказ | Неуспешная финальная стадия | Отказ закрывает сделку и убирает её из активной работы |

Главное правило модели данных: **один гость — один контакт; каждое обращение или бронирование — отдельная сделка**.

## Модель данных

### Контакт гостя

| Поле | Тип | Обязательность | Пример |
| --- | --- | --- | --- |
| Имя | Стандартное текстовое поле | Обязательно | Иван Петров |
| Телефон | Стандартное поле телефона | Обязательно | +7 999 123-45-67 |

Телефон используется как основной признак поиска существующего гостя. Перед созданием нового контакта администратор должен выполнить поиск по номеру.

### Сделка бронирования

| Поле | Тип | Обязательность | Пример |
| --- | --- | --- | --- |
| Название сделки | Стандартное текстовое поле | Обязательно | Иван Петров, 12–15 октября |
| Клиент | Связь с контактом | Обязательно | Иван Петров |
| Дата заезда | Пользовательское поле Дата | Обязательно | 12.10.2026 |
| Дата выезда | Пользовательское поле Дата | Обязательно | 15.10.2026 |
| Категория номера | Пользовательское поле Список | Обязательно | Комфорт |
| Количество гостей | Пользовательское поле Целое число | Обязательно | 2 |
| Комментарий | Стандартное текстовое поле или комментарий в таймлайне | Необязательно | Нужна детская кроватка |

Рекомендуемые значения поля «Категория номера»: «Стандарт», «Комфорт», «Люкс», «Семейный».

## Воронка бронирования

| Порядок | Стадия | Тип | Когда используется |
| --- | --- | --- | --- |
| 1 | Новое обращение | Активная | Звонок принят, карточка создана |
| 2 | Уточняем детали | Активная | Администратор выясняет даты, категорию или условия |
| 3 | Бронь подтверждена | Активная | Гость подтвердил приезд, бронь согласована |
| 4 | Гость заселился | Успешная финальная | Гость фактически приехал |
| 5 | Отказ от бронирования | Неуспешная финальная | Гость отказался или бронь не состоялась |

Переходы выполняются вручную. Автоматизация не требуется для выполнения критериев приёмки.

## Пользовательские сценарии

### Новое обращение и успешное заселение

1. Администратор получает звонок.
2. Ищет телефон в контактах.
3. Если гостя нет, создаёт новый контакт с именем и телефоном.
4. Создаёт связанную сделку.
5. Заполняет даты, категорию номера и количество гостей.
6. Сохраняет сделку на стадии «Новое обращение».
7. По мере работы перемещает её в «Уточняем детали» и «Бронь подтверждена».
8. После приезда переводит сделку в «Гость заселился».

### Отказ от бронирования

1. Администратор открывает активную сделку.
2. При необходимости добавляет комментарий с причиной отказа.
3. Перемещает сделку в «Отказ от бронирования».
4. Проверяет, что сделка отображается как неуспешно завершённая и не остаётся среди активных обращений.

### Повторный гость

1. Администратор ищет гостя по телефону.
2. Открывает существующий контакт.
3. Проверяет, что в контакте видна предыдущая сделка.
4. Создаёт новую сделку и связывает её с тем же контактом.
5. Заполняет новые даты и параметры бронирования.
6. Проверяет, что у контакта теперь отображаются обе сделки.

## Функциональные требования

- Система должна позволять создать контакт с именем и телефоном.
- Система должна позволять создать связанную с контактом сделку.
- В сделке должны сохраняться даты заезда и выезда, категория номера и количество гостей.
- Сделка должна проходить четыре заданные стадии.
- Отказ должен фиксироваться отдельной неуспешной стадией.
- Один контакт должен поддерживать несколько связанных сделок.
- Администратор должен находить существующего гостя по телефону.
- После завершения демо-режима все приёмочные сценарии должны оставаться доступными.

## Ограничения и требования к качеству

- Решение не должно требовать платной подписки.
- В реализации нельзя зависеть от функций, доступных только в демо-режиме.
- Названия полей и стадий должны точно соответствовать терминологии задания.
- Тестовые телефоны не должны принадлежать реальным людям.
- Перед записью видео нужно удалить или скрыть случайные учебные данные, не относящиеся к демонстрации.
- Интерфейс должен быть понятен пользователю без отдельного обучения.

## План проверки перед сдачей

### Быстрая проверка данных

- У каждой тестовой сделки заполнены даты заезда и выезда.
- Дата выезда позже даты заезда.
- Выбрана категория номера.
- Количество гостей больше нуля.
- Сделка связана с правильным контактом.
- У повторного гостя используется тот же телефон и тот же контакт.

### Быстрая проверка процесса

- В активной части воронки находятся только незавершённые обращения.
- «Гость заселился» является успешной финальной стадией.
- «Отказ от бронирования» является неуспешной финальной стадией.
- Воронка содержит только этапы, необходимые заданию.

### Быстрая проверка тарифа

- На портале указан тариф «Бесплатный».
- Демо-режим отключён или завершён.
- После этого контакты, сделки, поля и стадии по-прежнему доступны.
- Приёмочные сценарии повторно проверены в фактическом бесплатном режиме.

## Риски и способы их снизить

| Риск | Последствие | Действие |
| --- | --- | --- |
| Настройка выполнена во время демо-режима | После окончания демо часть функций перестанет работать | Отключить демо заранее и повторить все тесты |
| Использованы лиды | Процесс усложняется и может зависеть от тарифа | Использовать простой режим CRM, контакты и сделки |
| Создаются дубли гостей | История повторного гостя разделяется между карточками | Всегда искать контакт по телефону перед созданием нового |
| Отказ сделан обычной активной стадией | Отказные сделки остаются среди текущей работы | Использовать неуспешную финальную стадию |
| Поля не заполнены | Приёмочный сценарий не соответствует заданию | Проверять карточку по чек-листу перед сохранением и съёмкой |
| Видео не доказывает тариф | Работа формально не проходит приёмку | Включить отдельный фрагмент с тарифом и статусом демо |

## Правила внесения изменений

- Сначала проверить, требуется ли изменение критериями клиента.
- Не добавлять платные функции без отдельного согласования.
- Не менять основное правило «контакт — гость, сделка — бронирование» без пересмотра всей модели.
- Новое поле добавлять только тогда, когда понятно, кто и в каком сценарии его заполняет.
- После изменения стадий или полей повторить три приёмочных сценария.
- Существенные решения фиксировать в разделе «Журнал решений».

- почему отказ является финальной неуспешной стадией;
- каким экраном подтверждается работа на бесплатном тарифе.

## Определение готовности проекта

Проект готов к сдаче, когда одновременно выполнены следующие условия:

- портал работает на бесплатном тарифе без активного демо-режима;
- настроены все поля и стадии;
- три приёмочных сценария проходят без ошибок;
- повторный гость имеет один контакт и минимум две связанные сделки;
- отказ отображается отдельно от успешных бронирований;
- записано и проверено демонстрационное видео;
- ссылки и материалы сдачи доступны проверяющему.

## Термины

**Контакт** — карточка физического лица с именем, телефоном и связанной историей.

**Сделка** — отдельное обращение гостя по конкретным датам проживания.

**Воронка** — последовательность стадий, по которым проходит сделка.

**Активная стадия** — этап, на котором обращение ещё требует работы.

**Успешная стадия** — завершение сделки с нужным результатом, в этом проекте с заселением гостя.

**Неуспешная стадия** — завершение сделки без бронирования или заселения.

**Демо-режим** — временный доступ к расширенным функциям Bitrix24, который не должен быть основой финального решения.
